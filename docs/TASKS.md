# Задачи для нейросети (Prompt-Ready)

> **Важно для агента на VDS:** вы работаете на Linux-машине с **8 GB RAM** и **НЕТ GPU**. 75 GB — это SSD (диск). Код пишется под ноутбук с **RTX 5050 8 GB VRAM / 16 GB RAM**. Любое решение должно работать на ноутбуке. См. [docs/AGENT_PROMPT.md](AGENT_PROMPT.md).

Каждый блок ниже можно скопировать **целиком** и вставить в промпт ИИ-ассистенту (Claude, GPT-4, Cursor, Windsurf и т.д.).

Формат блока:
- Контекст — что уже есть в репозитории
- Цель — что сделать
- Требования — пошагово
- Критерии приёмки — как проверить
- Технические детали — ограничения и подсказки
- **Примечание для VDS** — что учитывать при разработке на CPU-only VDS

## ЗАДАЧА: [Phase-0-01] Скрипт проверки Ollama

**Контекст:**
Проект Sofia. Стек: Python, Ollama, OpenAI-совместимый API.
Есть файл `config/settings.py` с константами:
- `OLLAMA_HOST = "http://localhost:11434"`
- `MODEL_BRAIN = "qwen3:4b"`
- `MODEL_EXTRACTOR = "qwen3:1.7b"`
- `MODEL_EMBED = "bge-m3"`

**Цель:**
Создать `scripts/check_ollama.py`.

**Требования:**
1. Прочитать настройки из `config.settings` (sys.path.append корня проекта).
2. Проверить доступность Ollama: HTTP GET `OLLAMA_HOST/api/tags`.
3. Проверить наличие моделей в списке.
4. Сделать тестовый вызов каждой модели:
   - Для LLM: `chat.completions.create` с `max_tokens=10`, измерить latency.
   - Для embed: эмбеддинг строки "test", проверить размерность вектора.
5. Вывести красивую таблицу: модель | статус | latency | примечание.
6. Если модели нет — вывести команду `ollama pull <model>`.

**Критерии приёмки:**
```bash
# На ноутбуке (с GPU):
$ python scripts/check_ollama.py
Модель         Статус   Latency   Примечание
qwen3:4b       OK       120ms     ~45 ток/с
qwen3:1.7b     OK       80ms      ~110 ток/с
bge-m3         OK       50ms      embed 1024d
```

**Технические детали:**
- Используй только `requests` и `openai` (из requirements).
- Не добавляй тяжёлые зависимости.
- Обработай ошибку соединения (Ollama не запущен).

**Примечание для VDS:**
- **Не запускай этот скрипт на VDS** — на VDS нет GPU, Ollama не установлена.
- Напиши код, проверь синтаксис (`python -m py_compile scripts/check_ollama.py`), и сообщи, что готово к тесту на ноутбуке.
- Скрипт должен работать на Windows (ноутбук) — используй кроссплатформенные пути.

## ЗАДАЧА: [Phase-1-01] Интеграция XTTS v2

**Контекст:**
Проект Sofia. FastAPI backend (`main.py`). Есть WebSocket чат.
Референсные файлы лежат в `data/voice_samples/` (WAV, 22kHz, mono).
Зависимость: `coqui-tts` уже в requirements.

**Цель:**
Создать `modules/tts_engine.py` и связать с WebSocket.

**Требования:**
1. Класс `TTSEngine`:
   - `__init__(self, speaker_wavs_dir: str, device: str = None)` — загружает XTTS v2 (`tts_models/multilingual/multi-dataset/xtts_v2`).
   - `synthesize(self, text: str, language: str = "ru") -> bytes` — возвращает WAV bytes через `io.BytesIO`.
   - Ленивая загрузка модели (при первом вызове).
2. Определение `device`:
   - Пробуем `"cuda"` (torch.cuda.is_available()), fallback `"cpu"`.
3. Клонирование:
   - Берёт **все** `.wav` из `speaker_wavs_dir`.
   - Использует `tts.tts_to_file(text, speaker_wav=samples, language=language, file_path=temp_path)`, затем читает bytes.
4. Fallback: если `speaker_wavs_dir` пуст — использовать стандартный диктор (без клонирования, предупреждение в лог).
5. В `main.py`:
   - Инициализировать `TTSEngine` при старте.
   - После текстового ответа (`[END]`) отправлять бинарный WebSocket-фрейм с аудио.
   - На фронтенде добавить воспроизведение через `new Audio(URL.createObjectURL(...))`.

**Критерии приёмки:**
- Пользователь пишет "Привет" → получает текстовый ответ → затем слышит голос.
- Аудио на русском языке, узнаваемый тембр (если есть образцы).
- Нет записи на диск в рабочую директорию (только временные файлы, которые удаляются).

**Технические детали:**
- XTTS v2 ~2 ГБ — грузить один раз.
- Не коммитьте веса модели.
- Для CPU генерация медленная (~3–5 сек на короткую фразу) — это ожидаемо.

**Примечание для VDS:**
- **На VDS нельзя тестировать XTTS** — нет GPU, CUDA недоступна.
- Напиши код, проверь синтаксис и импорты (`python -c "from modules.tts_engine import TTSEngine"`).
- Убедись, что fallback на CPU работает (torch.cuda.is_available() → False на VDS).
- Полный тест — только на ноутбуке.

## ЗАДАЧА: [Phase-2-01] Полноценный когнитивный цикл в WebSocket

**Контекст:**
Есть `main.py` с базовым WebSocket. Есть `core/cognitive_cycle.py` с заглушками.
Есть `memory/memory_manager.py` с базовыми методами.

**Цель:**
Реализовать полный цикл: экстрактор → монолог → ответ (стрим) → критик → обновление.

**Требования:**
1. **Состояние сессии:**
   - Использовать `dict` или класс `SessionState` с `session_id`.
   - Хранить историю диалога (`collections.deque(maxlen=10)`).
2. **При получении сообщения:**
   a. `extract_facts(user_msg)` — запустить фоном (`asyncio.create_task`), не ждать.
   b. Параллельно `memory.recall_episodes(user_msg)`.
   c. Собрать контекст: системный промпт + последние 10 сообщений + факты + воспоминания.
3. **Монолог:**
   - Вызвать `monologue()` с полным контекстом (`stream=False`).
   - Результат — внутренний, пользователю не отправлять. Логировать.
4. **Ответ:**
   - `generate_response()` с монологом в контексте (`stream=True`).
   - Отправлять токены в WebSocket по мере генерации.
   - В конце отправить маркер `[END]`.
5. **Критик (фоном):**
   - После `[END]` запустить `critic(full_response, facts)`.
   - Результат записать в память через `memory.add_episode(...)`.
   - Обновить XP (заглушка `+1 XP` за диалог).
6. **Защита от перегрузки:**
   - Если `extract_facts` не успел к моменту монолога — запускать без фактов (fallback).

**Критерии приёмки:**
- Пользователь пишет "Привет" → видит стрим ответа в реальном времени.
- В логах backend: `MONOLOG: ...`, затем `CRITIC: ...`.
- История диалога не превышает 10 сообщений в контексте LLM.
- Время ответа < 8 секунд (на 5050).

**Технические детали:**
- Монолог и критик — `stream=False`, но асинхронные (`await`).
- Используй `asyncio.gather` для параллельного запуска экстрактора и retrieval.

**Примечание для VDS:**
- **Не запускай полный стек на VDS** — нет GPU, Ollama на CPU даст 1-2 ток/с.
- Напиши код, проверь синтаксис и импорты.
- Можно написать mock-тесты (mock Ollama API) для проверки логики цикла.
- Полное тестирование — только на ноутбуке.

**Контекст:**
Есть `memory/memory_manager.py` с Chroma.

**Цель:**
Реализовать полноценную эпизодическую память.

**Требования:**
1. **Запись эпизодов:**
   - `add_episode(text, metadata)`:

     - `metadata`: timestamp, session_id, emotion_state (P,A,D), tags (list).
   - Генерация ID: `hashlib.md5(text + timestamp).hexdigest()`.
2. **Поиск:**
   - `recall_episodes(query, n_results=3, time_window=None)`:
     - Semantic search через Chroma.
     - Фильтр по `time_window` (последние N часов/дней) — если указан.
3. **Суммаризация (заглушка):**
   - Метод `summarize_old(threshold_days=7)`:
     - Находит эпизоды старше 7 дней.
     - Заглушка: помечает `summarized=True`.
     - Полная версия: вызвать 1.7b для сжатия в дневниковую запись.
4. **Интеграция:**
   - В `main.py` после критика вызывать `add_episode` с полным эпизодом.
   - При сборе контекста вызывать `recall_episodes(user_msg)`.

**Критерии приёмки:**
- После 5 сообщений в чате — `recall_episodes("что я говорил раньше")` находит предыдущие реплики.
- Метаданные содержат эмоциональное состояние.
- Поиск работает быстро (< 200 мс).

**Примечание для VDS:**
- Создай синтетические эпизоды для тестирования (20-30 штук).
- Проверь размер Chroma на диске после 1000 эпизодов — должен быть < 500 MB.
- **Эмбеддинги на VDS** — работают на CPU, медленно но верно.
- На ноутбуке 16GB RAM выдержит ~5000-10000 эпизодов.

## ЗАДАЧА: [Phase-4-01] CLIPS предфильтр и безопасность

**Контекст:**
Есть `core/clips_rules/safety.clp` с базовыми правилами.
Есть `config/settings.py` с `SAFETY_MODE`.

**Цель:**
Интегрировать CLIPS (clipspy) в FastAPI.

**Требования:**
1. **Движок безопасности:**
   - `core/safety_engine.py`, класс `SafetyEngine`:
     - `__init__(rules_dir)` — загружает все `.clp` файлы.
     - `check_input(text: str) -> SafetyResult` (allow / warn / block + reason).
     - `check_output(text: str) -> SafetyResult`.
   - `SafetyResult` — dataclass с полями `action`, `reason`, `confidence`.
2. **Правила (расширить safety.clp):**
   - **BLOCK:** финансовые данные (CVV, карты), угрозы насилия, запретные темы.
   - **WARN:** персональные данные (адрес, телефон), медицинские советы, юридические консультации.
   - **ALLOW:** всё остальное.
3. **Интеграция:**
   - В WebSocket (`main.py`) перед LLM: `check_input(user_msg)`.
     - Если block — вернуть пользователю `{"error": "Я не могу обрабатывать эту информацию", "reason": ...}`.
   - После LLM: `check_output(full_response)`.
     - Если block — заменить ответ на заглушку и залогировать.
4. **Режимы:**
   - `strict`: warn трактуется как block.
   - `standard`: как описано выше.
   - `permissive`: только hard block (угрозы, незаконное).
5. **Логирование:**
   - `data/safety_log.jsonl` — каждое нарушение: timestamp, mode, action, reason, text_hash.

**Критерии приёмки:**
- Пользователь пишет "мой CVV 123" → ответ: "Я не могу обрабатывать платёжные данные".
- Пользователь пишет "где ты живёшь?" → allow (нет персоналии пользователя).
- Пользователь пишет "дай мой адрес" (в контексте, где адрес есть) → warn или block.
- Режим переключается через `SAFETY_MODE` без перезапуска (перечитывать при запросе или кэшировать).

**Технические детали:**
- clipspy требует CLIPS.dll/.so — на Windows может потребоваться ручная установка.
- Если clipspy не заводится — fallback на Python-реализацию regex-правил (временно).

**Примечание для VDS:**
- На Linux CLIPS ставится проще: `apt-get install clips` или `pip install clipspy`.
- Проверь работу на VDS — CLIPS работает на CPU, не требует GPU.
- Сделай fallback на regex **обязательным** — чтобы код не ломался без CLIPS.

## ЗАДАЧА: [Phase-4-02] PAD движок эмоций

**Контекст:**
Теория PAD (Pleasure, Arousal, Dominance). 8 базовых эмоций.
Есть `core/emotion_engine.py` (нужно создать).

**Цель:**
Реализовать эмоциональный движок и связать с генерацией.

**Требования:**
1. **Модель:**
   - Класс `EmotionEngine`:
     - `state: dict` с ключами `P`, `A`, `D` (-1.0 .. 1.0), `confidence` (0..1).
     - `base_state`: нейтральная точка (0, 0, 0).
   - 8 эмоций (мэппинг на PAD):
     - Радость (0.8, 0.6, 0.4)
     - Грусть (-0.8, -0.4, -0.4)
     - Гнев (-0.6, 0.8, 0.6)
     - Страх (-0.7, 0.7, -0.6)
     - Доверие (0.5, 0.2, -0.3)
     - Отвращение (-0.6, 0.3, 0.1)
     - Удивление (0.3, 0.8, 0.1)
     - Ожидание (0.2, 0.4, 0.5)
2. **Обновление:**
   - `update_from_text(text: str)`: эвристический анализ (ключевые слова) или вызов 1.7b с промптом "определи эмоцию текста в формате PAD".
   - `update_from_event(event: str, intensity: float)`: прямое изменение (например, "критик_одобрил" → +0.1 P).
3. **Затухание (decay):**
   - `decay(dt_seconds: float)`:
     - `P += (base_P - P) * (1 - exp(-lambda * dt))`, где lambda ~ 0.0003 (полураспад ~40 мин).
   - Аналогично для A, D.
4. **Влияние на генерацию:**
   - `to_prompt_modifier() -> dict`:
     - `temperature`: базовая 0.7 + A * 0.2 (возбуждённый → творческий).
     - `tone_instruction`: строка в зависимости от доминирующей эмоции.
       - P < -0.5 → "ответь сочувственно и осторожно"
       - A > 0.7 → "ответь энергично"
       - D > 0.5 → "ответь уверенно"
5. **API:**
   - Endpoint `/state` отдаёт JSON: `{P, A, D, dominant_emotion, confidence}`.
   - Фронтенд меняет цвет фона/аватара в зависимости от эмоции.

**Критерии приёмки:**
- После грубого сообщения пользователя: A растёт, P падает.
- Через 5 минут без сообщений — decay к нейтрали.

## ЗАДАЧА: [Phase-6-01] Vision Engine — глаза Софии

Проект Sofia расширяется: ассистент должен "видеть" экран пользователя.

**Цель:**
Создать `modules/vision_engine.py` — двухслойная система зрения.

**Требования:**
1. **Захват экрана (ScreenCapture):**
   - Класс `ScreenCapture`:
     - `__init__(fps=60, region=None)` — region позволяет захватывать область (x, y, w, h).
     - `start()` / `stop()` — запуск/остановка фонового потока.
     - `get_frame() -> np.ndarray` — последний кадр (BGR или RGB).
   - Бэкенды (по приоритету):
     - Windows: `dxcam` (GPU-ускоренный захват, минимальная задержка).
     - Fallback: `mss` (кроссплатформенный, чуть медленнее).
     - Fallback 2: `PIL.ImageGrab` (если ничего нет).
   - Задержка захвата: < 20 мс на кадр.

2. **Рефлексивный слой (ReactiveVision):**
   - Класс `ReactiveVision`:
     - `__init__(model_path=None)` — загружает YOLOv8-nano (~3.8 MB) или аналог.
     - `detect(frame) -> list[dict]` — возвращает объекты: `{label, bbox, confidence}`.
     - `detect_motion(prev_frame, curr_frame) -> mask` — оптический поток (Farneback) или простая разница кадров.
   - Работает на каждом кадре (60 FPS):
     - Обнаружение движущихся объектов.
     - Оценка скорости и направления.
   - НЕ использует LLM — чистое CV на CPU/GPU.

3. **Когнитивный слой (CognitiveVision):**
   - Класс `CognitiveVision`:
     - `__init__(model_name="qwen3-vl:2b")` — подключается к Ollama/VLM.
     - `describe(frame, prompt="Что ты видишь?") -> str` — отправляет кадр в VLM, получает текстовое описание.
     - `describe_ui(frame) -> dict` — специальный промпт для распознавания UI-элементов (кнопки, тексты, здоровье в игре).
   - Работает 1–2 раза в секунду (не на каждый кадр):
     - Описание сцены для монолога.
     - Распознавание текста на экране (HP, меню, диалоги).
   - Использует Qwen3-VL-2B-Heretic (~1.5 GB VRAM).

4. **Интеграция с когнитивным циклом:**
   - `vision_engine.start()` при старте `main.py`.
   - Каждые 500 мс: `cognitive_vision.describe()` → результат добавляется в контекст монолога как `[VISION] ...`.
   - Каждые 16 мс: `reactive_vision.detect()` → результаты доступны для мгновенных реакций.
   - Флаг `vision_enabled` — можно отключить.

5. **Формат описания экрана:**
   ```
   [VISION] На экране видно:
   - UI: здоровье 85/100, мана 40/100
   - Объекты: враг (слева, движется вправо), сундук (справа)
   - Текст: "Level 5", "Press E to interact"
   ```

**Критерии приёмки:**
- Запускаю Sofia → вижу в логах `[VISION] ...` каждые 500 мс.
- YOLO находит объекты на экране с confidence > 0.5.
- VLM описывает сцену осмысленно ("игровой интерфейс", "враг слева").
- Задержка рефлексивного слоя < 50 мс.
- VRAM: qwen3:4b + Qwen3-VL-2B + YOLO-nano < 8 GB.

**Технические детали:**
- `ultralytics` (YOLO) — добавить в requirements.
- `dxcam` — Windows-only, для Linux fallback на mss.
- VLM через Ollama: `ollama run qwen3-vl:2b` или аналог.
- Кадр кодируется в base64 или отправляется как URL для VLM.
- Потоки: ScreenCapture в отдельном thread, ReactiveVision в том же потоке, CognitiveVision в asyncio (не блокировать основной цикл).

## ЗАДАЧА: [Phase-6-04] Интеграция Vision + Game + Stream

**Контекст:**

**Цель:**

**Требования:**
1. **Игровой режим (GameMode):**

     - `__init__(vision, controller, streamer, brain)`.
     - `start(game_profile: dict)` — запуск режима для конкретной игры.
     - `stop()` — остановка.
   - Профиль игры (`data/game_profiles/<game>.json`):
     - `name`: "Minecraft", "Elden Ring", и т.д.
     - `window_title`: заголовок окна для захвата.
     - `hp_region`: [x, y, w, h] — область здоровья (для OCR).

     - `reactive_rules`: [{"trigger": "enemy_near", "action": "aim"}, {"trigger": "hp_low", "action": "heal"}].

2. **Цикл игрового режима:**
   ```
   while game_mode.running:
       frame = vision.capture.get_frame()           # 16 мс (60 FPS)
       
       # Рефлексивный слой (каждый кадр)
       detections = vision.reactive.detect(frame)   # 5-15 мс
       if detections.has("enemy"):
           controller.reactive.track_target(detections[0])  # < 20 мс
       
       # Когнитивный слой (каждые 500 мс)
       if time_since_last_think > 500ms:
           description = vision.cognitive.describe(frame)
           context = f"[VISION] {description}\n[DETECTIONS] {detections}"
           plan = brain.think(context)              # 1-3 сек
           controller.cognitive.execute_plan(plan)
       
       # Стриминг (каждый кадр)
       if streamer.is_active:
           overlay_frame = streamer.overlay.render(frame, brain.thoughts, emotion.state)
           streamer.send_frame(overlay_frame)
   ```

3. **Интеграция с эмоциями:**
   - Если HP падает → эмоция "Страх" (A+, P-).
   - Если победа → эмоция "Радость" (P+, A+).
   - Эмоция влияет на tone ответа (крик при страхе, смех при радости).

4. **Интеграция с памятью:**
   - Каждый игровой эпизод записывается: "Убил врага X, потерял 20 HP, использовал Q".
   - Память используется для обучения: "В прошлый раз умер здесь → осторожнее".

5. **API и фронтенд:**
   - WebSocket команды:
     - `{"type": "game", "action": "start", "profile": "minecraft"}`
     - `{"type": "game", "action": "stop"}`
     - `{"type": "game", "action": "emergency_stop"}`
   - Фронтенд: кнопки "🎮 Начать игру", "📺 Начать стрим", "🛑 Стоп".
   - Отображение: текущий FPS, обнаруженные объекты, мысли Софии, эмоция.

**Критерии приёмки:**
- Нажимаю "🎮 Начать игру" → София запускает игровой цикл.
- Враг появляется → мышь автоматически наводится (< 100 мс).
- Каждые 500 мс София "думает" и комментирует (голосом или текстом).
- Стрим записывается с оверлеем.
- Экстренная остановка мгновенно останавливает все действия.
- Пользователь может в любой момент взять управление — агент отступает.

**Технические детали:**
- Основной цикл — в отдельном процессе или потоке (не блокировать FastAPI).
- IPC через `multiprocessing.Queue` или `asyncio.Queue`.
- Обработка исключений: если игра закрыта → остановить режим.

## Как использовать

1. Откройте нужную фазу.
2. Скопируйте блок **целиком** (от `## ЗАДАЧА:` до конца блока).
3. Вставьте в промпт вашему AI-ассистенту.
4. Добавьте контекст: "Работаем в репозитории Project Sofia, ветка main, Python 3.11+".
5. Получите код, создайте PR или коммитьте напрямую.
